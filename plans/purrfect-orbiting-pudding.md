# モデル型設計書のエントリポイント非表示計画

## Context（背景・目的）

### 問題
現状、すべての種別（画面・API・バッチ・モデル）の設計書でエントリポイント入力欄が表示されているが、**モデル型にはエントリポイントの概念が適用できない**。

### エントリポイントの本来の用途
エントリポイントは「処理の開始点」を示すもの：
- **画面**: ボタンクリック、ページ遷移
- **API**: HTTPエンドポイント
- **バッチ**: 定期実行ジョブ、イベントトリガー

### モデルには不適用
**モデル**はテーブル定義（静的なデータ構造）を表現するもので、処理の開始点は存在しない。依存関係ツリーを調べる際の起点にもならない。

### 改善の方向性
モデル型の場合のみ、エントリポイント入力欄を非表示にする。

- **データは保持する**（既存データや将来の用途変更に備える）
- **UIのみ非表示**（条件分岐で表示制御）

## 実装内容

### 1. 詳細画面（ビューア）の変更

**ファイル**: `components/system-domains/structured-spec-viewer/index.tsx`

**変更箇所**: 40-46行目

**Before**:
```tsx
{/* エントリポイント */}
{spec.entryPoints && spec.entryPoints.length > 0 && (
  <div>
    <Label className="text-sm font-medium">エントリポイント</Label>
    {/* ... */}
  </div>
)}
```

**After**:
```tsx
{/* エントリポイント（モデル型以外のみ表示） */}
{!isModelType && spec.entryPoints && spec.entryPoints.length > 0 && (
  <div>
    <Label className="text-sm font-medium">エントリポイント</Label>
    {/* ... */}
  </div>
)}
```

**ポイント**:
- 既に他のセクション（例: 60行目以降）で `{!isModelType && ...}` パターンが使われている
- 同じパターンを適用するだけで一貫性が保たれる

---

### 2. 編集画面の変更

**ファイル**: `components/forms/design-document/DesignDocumentCard.tsx`

**変更箇所**: 1151-1160行目（おおよそ）

**Before**:
```tsx
{/* エントリポイント */}
<div className="space-y-2">
  <Label className="text-xs">エントリポイント</Label>
  {/* ... */}
</div>
```

**After**:
```tsx
{/* エントリポイント（モデル型以外のみ表示） */}
{spec.ioType !== "model" && (
  <div className="space-y-2">
    <Label className="text-xs">エントリポイント</Label>
    {/* ... */}
  </div>
)}
```

**ポイント**:
- ビューアでは `isModelType`（導出変数）を使用
- 編集画面では `spec.ioType !== "model"` で直接判定
- 既にこのパターンは他のセクションで使われている

## 影響範囲

### 変更ファイル

1. `components/system-domains/structured-spec-viewer/index.tsx` - 詳細画面のエントリポイント非表示
2. `components/forms/design-document/DesignDocumentCard.tsx` - 編集画面のエントリポイント非表示

### 影響を受ける機能

- モデル型設計書の編集画面（エントリポイント入力欄が非表示になる）
- モデル型設計書の詳細画面（エントリポイント表示欄が非表示になる）

### 影響を受けないもの

- 画面・API・バッチ型の設計書（変更なし、引き続きエントリポイント表示）
- データベース（既存のエントリポイントデータは保持される）
- 他のコンポーネント・機能

## リスクと対策

### リスク1: 既存のモデル型設計書にエントリポイントデータがある場合

**リスク**: 非表示になるだけでデータは残るため、ユーザーが混乱する可能性

**対策**:
- データは保持する（将来、種別を変更した場合に再利用できる）
- 非表示であることを明示的に伝える必要はない（UIに存在しないだけ）
- 必要であればマイグレーションで削除することも可能だが、YAGNI原則に従い今は実施しない

### リスク2: 将来の仕様変更

**リスク**: 将来、モデルにもエントリポイントが必要になる可能性

**対策**:
- データを保持しているため、条件分岐を削除するだけで復元可能
- 設計判断を変更するコストは低い

### リスク3: 実装漏れ

**リスク**: 編集画面と詳細画面で条件分岐を忘れる箇所がある

**対策**:
- E2Eテストで全種別をテストする
- 既存の類似パターンを参考にする

1. **編集画面の変更**（`DesignDocumentCard.tsx`）
   - エントリポイント入力欄を `{spec.ioType !== "model" && ...}` でラップ

2. **詳細画面の変更**（`StructuredSpecViewer/index.tsx`）
   - エントリポイント表示欄を `{!isModelType && ...}` でラップ

3. **動作確認**（E2E テスト）
   - agent-browser で各種別の表示を確認
   - スクリーンショットを取得して検証

4. **ドキュメント更新**（任意）
   - PRD.md に「モデル型にはエントリポイント不要」を明記

### YAGNI 原則の適用

- **エントリポイントデータの削除**: 不要なので実施しない（保持しても害はない）
- **マイグレーションスクリプト**: 不要（UI非表示のみ）
- **将来の拡張**: 必要になった時点で条件を削除すればよい
