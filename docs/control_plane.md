# 実装Control PlaneのためのSR/AC/DD品質担保ガイド

## 1. なぜ品質担保が必要か

コーディングエージェントは「指示された範囲を高精度に実装する」能力を持ちますが、**「何を直すべきか」「どこまで触ってよいか」「何をもって完成とするか」** が曖昧だと、人間の意図と異なる実装を行うリスクが高まります。

ここで必要となるのが **実装のcontrol plane** です。これは「実装を統制するための仕様と手順」を指し、以下を同時に実現します。

- **スコープの固定**：変更対象をファイル単位で特定し、想定外の改変（越境変更）を防ぐ
- **検証の自動化**：期待結果をテストコードでアサート可能な形にし、人間の判断に依存しない合格基準を作る
- **変更の追跡性**：「なぜその仕様になったか」を記録し、後から要求と実装の対応関係を再現できるようにする

このcontrol planeを成立させる3要素（SR/AC/DD）の記述ルールを以下に定義します。

---

## 2. 3つの成果物の定義と責務分界

### SR（System Requirements）：システムが保証する「契約の本文」
**定義**：ユーザー視点で「システムが何を保証すべきか」を記述したもの。内部実装の詳細ではなく、入出力と振る舞いの仕様を固定します。

**責務**：機能要件・データ要件・例外要件・非機能要件の4観点から、変更してはいけない「不変条件」を明記します。

### AC（Acceptance Criteria）：契約を「検証可能」にする受入基準
**定義**：SRを満たしているかを客観的に判定できる、GWT（Given-When-Then）形式の検証条件群。

**責務**：テスト自動化可能なアサーションを記述し、「この結果が出たらOK」という判定基準を機械的に実行できるようにします。

### DD（Design Detail）：契約を「コードに接続」する設計詳細
**定義**：SR/ACを実装するにあたり、「どのファイルを変更し」「どの境界で責務を分離するか」を記述したもの。

**責務**：エントリポイント（変更の入口となるファイル）と変更境界（トランザクション・認可・冪等性の境界）を特定し、AIが変更すべきスコープ（allow paths）を物理的に制限します。

---

## 3. 記述の基本方針

### 方針A：SRは具体性を持たせる
「入力を定義する」という曖昧な指示ではなく、以下の要素を**必ず**含めます。

| 要素 | 具体的内容 | 記述例 |
|------|-----------|--------|
| **データスキーマ** | 型（string/number/boolean/enum/object）、必須/任意、デフォルト値 | `amount: number (必須, 0以上), currency: enum['JPY','USD'] (デフォルト: 'JPY')` |
| **許容範囲（制約）** | 文字数制限、数値範囲、フォーマット（正規表現）、権限 | `0 ≤ amount ≤ 999,999,999`、 `customer_id: /^C[0-9]{6}$/`、 `role: 'admin' or 'editor'` |
| **出力外形** | 返却データのスキーマ、HTTPステータス、エラーレスポンスの形式 | `200 OK: { invoice_id: string, total: number }`、 `404: { error_code: 'INVOICE_NOT_FOUND' }` |
| **状態変化（副作用）** | DBテーブルのCRUD、外部API呼び出し、イベント発行、ファイル出力 | `invoices.statusを'draft'→'issued'に更新`、`InvoiceIssuedイベントを発行` |
| **不変条件** | 処理前後で変わってはいけない整合性条件 | `請求金額合計 = 明細金額合計`、`発行済み請求書の金額は変更不可` |

### 方針B：ACは「アサーション可能」にする
「適切に処理される」などの主観的表現を禁止し、以下の**観測可能な事象**で記述します。

| 観測対象 | 具体的内容 | GWTのThenの書き方 |
|---------|-----------|------------------|
| **データ状態** | DBの特定レコードのカラム値、件数 | `invoicesテーブルのstatusが'issued'である` |
| **レスポンス外形** | JSONの特定フィールド値、配列長 | `response.invoice_idが'INV-2025-001'である` |
| **画面表示** | 特定DOM要素のテキスト、属性、表示/非表示 | `画面上に'発行完了'のトーストが表示される` |
| **ログ出力** | 特定のログレベル・メッセージ・構造化データ | `structured_logに{ event: 'invoice_issued', user_id: 'U001' }が出力される` |
| **副作用の発生** | 外部APIへのリクエスト、メール送信、ファイル生成 | `mockしたメール送信APIが1回呼ばれる`、 `/tmp/invoices/INV-001.pdfが生成される` |

### 方針C：DDは「物理的な作用点と論理的な境界」を確定させる
「設計を深く書く」ことではなく、以下の**具体的な紐付け**を行います。

| 項目 | 具体的内容 | 記述例 |
|------|-----------|--------|
| **エントリポイント** | ファイルパス、クラス名、関数名、APIエンドポイント | `src/features/billing/api/issue-invoice.ts`、 `POST /api/billing/invoices` |
| **変更境界（トランザクション）** | トランザクションの開始・終了位置、ロールバック条件 | `useCase層でトランザクション開始→Repository操作完了後にコミット`、 `エラー時は全てロールバック` |
| **変更境界（認可）** | 権限チェックの実行位置、失敗時の挙動 | `APIレイヤーのmiddlewareでbilling:invoice:issue権限をチェック`、 `権限不足時は403を即座に返す` |
| **変更境界（冪等性）** | 冪等キーの指定、重複リクエストの判定基準 | `idempotency-keyヘッダーによる判定`、 `同じキーの2回目以降は202 Acceptedを返す` |
| **Allow Paths** | 変更を許可するディレクトリ・ファイルパスのグロブパターン | `src/domain/billing/**`、 `src/app/api/billing/invoices/**`、 `!src/domain/billing/constants.ts`（変更禁止） |

## 4. 運用プロセス（変更要求から実装まで）

変更要求（CR）を受けてから実装完了までの流れを、control planeの観点から整理します。

1. **要求の構造化**  
   自然文/PDF/画面キャプチャから、SRの4要素（入力・出力・状態変化・不変条件）を抽出します。

2. **SRの作成**  
   データスキーマ（型・制約）と不変条件を明記します。「高速に」などの曖昧語は、具体的なレスポンスタイム（例：P95で200ms以内）に変換します。

3. **ACの作成**  
   SRごとに、正常系・異常系・境界値の3パターンをGWT形式で記述。Then節は必ず「DBのXテーブルのYカラムがZである」など、自動検証可能な形にします。

4. **DDの作成**  
   エントリポイントをファイルパスで指定し、トランザクション境界・認可境界・冪等性境界をコードのどの行（またはどのレイヤー）で担保するかを明記します。

5. **自動採点（品質ゲート）**  
   以下の観点で0〜2点採点。いずれかが4点未満（満点6点中）の場合、レビューに進めません。
   - SR：スキーマ定義の有無・制約の明確性・例外定義の有無
   - AC：自動検証可能性・正常/異常カバレッジ・境界値の有無
   - DD：エントリポイントのファイルパス指定・変更境界の明示・Allow Pathsの定義

6. **ベースライン化**  
   合格したSR/AC/DDと、それらの依存関係（リンク）をスナップショットとして保存。これ以降の変更は、必ずこのベースラインとの差分として管理されます。

7. **影響範囲の特定**  
   ベースラインのリンクを辿り、変更が波及するSR・AC・ファイルパスを列挙します。

8. **改修指示パッケージの生成**  
   以下を含むパッケージを作成し、コーディングエージェントに投入します。
   - Allow Paths（変更可能なファイルのリスト）
   - 対象SR/ACのIDと内容
   - 変更前後の期待されるデータ状態（ACのThen節）

9. **実装と自動検証**  
   エージェントはAllow Paths内で実装を行い、ACのThen節を満たす単体テストを自動生成・実行します。

10. **ベースラインの更新**  
    変更が完了したSR/AC/DDのみを更新し、変更により信頼性が揺らいだリンク（疑義リンク）は「受信箱」に送り、次の変更時に優先的にレビューします。

## 5. SR（システム要件）の具体的内容

### 5.1 必須記述項目

以下のテーブルを埋める形で記述します。空欄があれば採点0点とします。

| 項目 | 記述内容 | 具体例 |
|------|---------|--------|
| **入力（Input Schema）** | パラメータ名・型・必須/任意・デフォルト値・制約条件 | `invoice_id: string, 必須, /^INV-[0-9]{6}$/` |
| **出力（Output Schema）** | 成功時の返却データ構造・HTTPステータス・失敗時のエラーコード一覧 | `200: { id, issued_at, pdf_url }`、 `409: { error: 'ALREADY_ISSUED' }` |
| **状態変化（Side Effects）** | 更新対象のDBテーブル・カラム・値の変化、発行されるイベント、外部API呼び出し | `UPDATE invoices SET status='issued'`、 `Event: InvoiceIssued発行` |
| **不変条件（Invariants）** | 処理前後で維持されなければならない整合性・計算式・業務ルール | `合計金額 = Σ(明細金額) + 消費税`、 `発行済み請求書の金額は不変` |
| **例外（Exceptions）** | 入力不備・権限不足・競合・外部エラー時の振る舞いとエラーレスポンス | `金額上限超過時：422 ValidationError`、 `DB接続失敗時：503 Retry-After付き` |

### 5.2 非機能要件の記述ルール

「高速」「安定」などの形容詞を禁止し、**測定可能な数値と条件**で記述します。

| 曖昧な表現 | 具体化した記述 |
|-----------|--------------|
| 高速に処理される | `P95で500ms以内（データ件数1万件以下の場合）` |
| 高可用性 | `月間可用率99.9%（月間ダウンタイム43分以内）` |
| 適切なログが出力される | `structured_json形式で、trace_id・user_id・処理時間(ms)を含む` |
| セキュア | `SQLインジェクション対策：プレースホルダ必須、XSS対策：出力エスケープ必須` |

## 6. AC（受入基準）の具体的内容

### 6.1 GWT形式の厳密な定義

Given-When-Thenの各セクションに、以下の**具体的な情報**を含めます。

**Given（前提条件）：**
- テストデータの具体的な値（ID、金額、日付など）
- DBの初期状態（特定レコードの存在とカラム値）
- ユーザーの権限・認証状態
- 外部サービスのモック状態（利用可能/停止中/遅延中など）

**When（実行操作）：**
- 呼び出すAPIエンドポイントとHTTPメソッド
- 送信するリクエストボディ（具体的なJSON）
- 画面操作の場合は、クリックするボタンのIDや入力フィールドのIDと値

**Then（期待結果）：**
- **検証可能なアサーション**（以下のいずれか以上）：
  1. DBの特定レコードのカラム値が期待値と一致する
  2. APIレスポンスの特定フィールドが期待値と一致する
  3. 特定のログが出力される
  4. モックした外部サービスの呼び出し回数・引数が期待値と一致する
  5. 画面の特定要素に期待するテキストが表示される（E2Eの場合）

### 6.2 カバレッジ要件

各SRに対して、以下のACを**必ず**作成します。

| パターン | 目的 | 例 |
|---------|------|-----|
| **正常系** | 標準的な入力での成功パターン | 正しい請求書IDで発行APIを呼ぶ→発行成功 |
| **異常系（入力不備）** | バリデーションエラー | 金額が負数→400エラー |
| **異常系（状態不備）** | ビジネスロジック違反 | 既に発行済み→409エラー |
| **異常系（権限）** | アクセス制御違反 | 権限なしユーザー→403エラー |
| **境界値** | 上限・下限・空値・最大長 | 金額が0円、明細が100件（上限）、空文字 |

## 7. DD（設計詳細）の具体的内容

### 7.1 エントリポイントの特定

以下の形式で、**ファイルパスまたは識別子**を列挙します。
[種別] [エントリポイントパス/識別子] [責務概要]
```
例：
API: src/features/billing/api/issue-invoice.ts
責務: 請求書発行のエンドポイント、認可チェック、バリデーション
Batch: jobs/nightly-tax-calc.ts
責務: 日次消費税計算バッチのエントリポイント
Screen: src/features/billing/pages/InvoiceDetailPage.tsx
責務: 請求書詳細画面の表示、発行ボタンの配置
```

### 7.2 変更境界の定義

| 境界の種別 | 定義内容 | 記述例 |
|-----------|---------|--------|
| **トランザクション境界** | トランザクションの開始・終了位置、ロールバック条件 | `InvoiceUseCase.execute()内でPrisma.$transaction開始`、 `例外発生時は全てロールバック` |
| **認可境界** | 権限チェックの実装場所、失敗時の挙動 | `API Route Handlerの最初でauthz.check('billing:issue')`、 `失敗時は即座に403返却` |
| **冪等性境界** | 冪等キーの受け渡し方法、重複検出ロジックの位置 | `ControllerでIdempotency-Keyヘッダーを受け取り、Redisで重複チェック`、 `重複時は保存済みレスポンスを返す` |
| **例外マッピング** | ドメイン例外とHTTPステータスの対応表 | `InvoiceAlreadyIssued → 409`、 `DatabaseConnectionError → 503` |

### 7.3 Allow Paths（変更許可範囲）

変更を許可するファイルを**グロブパターンまたは具体パス**で列挙します。これ以外のファイルを変更した場合、CIまたはレビューで自動的に拒否されます。

```yaml
allow_paths:
  - src/domain/billing/entities/Invoice.ts      # エンティティの修正
  - src/domain/billing/usecases/IssueInvoice.ts # ユースケースの修正
  - src/features/billing/api/issue-invoice.ts   # APIエンドポイントの修正
  - tests/billing/issue-invoice.test.ts         # テストの追加・修正

deny_paths:
  - src/domain/billing/constants.ts             # 税率定数は変更禁止（別CRで管理）
  - src/shared/utils/date.ts                    # 共通utilは変更禁止
```

## 8. 自動採点の具体的ルール

人の主観に依存せず、以下のルールで機械的に採点します。

### 8.1 SRの採点基準（各項目0〜2点）

| 項目 | 2点（満点） | 1点（部分点） | 0点（不可） |
|------|-----------|--------------|------------|
| 入力スキーマ | 全パラメータの型・必須性・制約（正規表現/範囲）が明記 | 型のみ記載、制約が不明確 | 記載なし、または「適切な入力」などの曖昧表現 |
| 出力スキーマ | 成功/失敗の両方のデータ構造とHTTPステータスが明記 | 成功時のみ記載、失敗時が不明 | 記載なし |
| 状態変化 | 更新対象テーブル・カラム・イベント発行が具体的に記載 | 「DBを更新」など抽象的 | 記載なし、副作用が不明 |
| 不変条件 | 数式・整合性ルールが明記（計算式、ユニーク制約など） | 部分的に記載 | 記載なし |
| 例外 | 全ての異常パターンと返却エラーが列挙 | 主要な例外のみ記載 | 「エラーは適切に処理」などの曖昧表現 |
| 非機能 | 数値基準（レスポンスタイム、可用率など）が明記 | 「高速」などの定性表現のみ | 記載なし |

**合格基準**：合計6点中4点以上、かつ0点の項目がないこと。
### 8.2 ACの採点基準（各項目0〜2点）

| 項目 | 2点（満点） | 1点（部分点） | 0点（不可） |
|------|-----------|--------------|------------|
| Given | テストデータの具体値（ID、金額など）とDB初期状態が明記 | 状態が抽象的（「適切なデータ」） | 前提が不明 |
| When | APIエンドポイント・メソッド・リクエストボディが明記 | 操作が抽象的（「処理を実行」） | トリガーが不明 |
| Then | 自動検証可能なアサーション（DB値・レスポンス・ログ）が明記 | 「正しく処理される」など主観的 | 検証方法が不明 |
| 正常系 | 標準的な成功パターンが記載 | - | 記載なし |
| 異常系 | 入力不備・状態不備・権限エラーのパターンが網羅 | 一部のみ記載 | 記載なし |
| 境界値 | 上限・下限・空値のパターンが記載 | 一部のみ記載 | 記載なし |

**合格基準**：合計6点中4点以上、かつThenが0点でないこと。
### 8.3 DDの採点基準（各項目0〜2点）

| 項目 | 2点（満点） | 1点（部分点） | 0点（不可） |
|------|-----------|--------------|------------|
| エントリポイント | ファイルパスまたは識別子が具体的に記載 | モジュール名のみ（ファイルパス不明） | 記載なし |
| トランザクション境界 | 開始・終了・ロールバックの位置が明記 | 「適切にトランザクション管理」など曖昧 | 記載なし |
| 認可境界 | チェック位置と失敗時の挙動が明記 | チェック有無のみ記載 | 記載なし |
| データモデル | 更新対象テーブル・カラムが列挙 | 「関連テーブル」など曖昧 | 記載なし |
| Allow Paths | 変更可能なファイルパスのリストが明示 | ディレクトリのみ（具体性不足） | 記載なし |
| 例外マッピング | ドメイン例外とHTTPステータスの対応表が明記 | 一部のみ記載 | 記載なし |

**合格基準**：合計6点中4点以上、かつエントリポイントとAllow Pathsが0点でないこと。
9. 記述例（税額計算ルールの変更）

以下は、抽象度の高い記述（悪い例）と、具体性を持たせた記述（良い例）の対比です。

### 9.1 SRの対比
**悪い例（抽象的）**：

```
・消費税を計算する
・入力は適切なデータ
・高速に処理される
・エラーは適切に処理
```

**良い例（具体的）**：

```yaml
対象: 仕入税額控除の計算処理

入力:
  - name: amount_with_tax
    type: integer
    required: true
    constraints: 0 ≤ value ≤ 999999999
  - name: tax_category
    type: enum
    values: [standard_10, reduced_8, exempt_0]
    required: true
  - name: deduction_rate
    type: enum
    values: [100, 80, 50, 0]
    required: true
  - name: rounding_method
    type: enum
    values: [floor, round, ceil]
    default: floor

出力:
  success:
    status: 200
    body:
      deductible_tax: integer (計算された控除税額)
      non_deductible_amount: integer (控除対象外額)
      calculation_basis: 
        formula: "税額 = floor(税込金額 × 税率 × 控除率)"
        applied_rate: 0.08 (適用された税率)
        applied_deduction_rate: 0.8 (適用された控除率)
  error:
    - status: 422
      when: 必須項目欠落または金額が負数
      body: { error_code: 'VALIDATION_ERROR', field: 'amount_with_tax' }

状態変化:
  - なし（計算のみ、永続化は呼び出し側で行う）

不変条件:
  - deductible_tax + non_deductible_amount = amount_with_tax - (amount_with_tax / (1 + tax_rate))
  - rounding_method=floorの場合、計算結果は1円未満切り捨て

非機能:
  - レスポンスタイム: P95で50ms以内（税込金額10億円以下の場合）
  - 同時実行: スレッドセーフであること
```

### 9.2 ACの対比
**悪い例（検証不能）**：

```
正常系: 正しい入力で計算される
異常系: エラーになる
```

**良い例（自動検証可能）**：

```yaml
正常系_標準税率:
  Given:
    - amount_with_tax: 11000 (整数)
    - tax_category: standard_10 (税率10%)
    - deduction_rate: 80 (控除率80%)
    - rounding_method: floor
  When: calculate_tax() を実行
  Then:
    - deductible_tax が 800 (11000 - 11000/1.1 = 1000 の80%)
    - non_deductible_amount が 200
    - calculation_basis.formula に "floor(11000 * 0.1 * 0.8)" が含まれる

異常系_金額超過:
  Given:
    - amount_with_tax: 1000000000 (10億、上限超過)
  When: calculate_tax() を実行
  Then:
    - status が 422
    - error_code が 'VALIDATION_ERROR'
    - DBにアクセスログが記録されない

境界値_0円:
  Given:
    - amount_with_tax: 0
  When: calculate_tax() を実行
  Then:
    - deductible_tax が 0
    - non_deductible_amount が 0
```

**悪い例（曖昧）**：

```
エントリポイント: 税計算モジュール

Allow Paths: src/tax/**
```

**良い例（具体的）**：

```yaml
エントリポイント:
  - API: src/app/api/tax/compute/route.ts
    責務: HTTPリクエスト受信、バリデーション、レスポンス返却
  - UseCase: src/domain/tax/usecases/CalculateTaxUseCase.ts

  - DomainService: src/domain/tax/services/TaxCalculator.ts

  トランザクション:
    - TaxCalculatorは純粋関数（副作用なし）
    - 計算結果の保存が必要な場合はUseCase層でトランザクション開始
    - 計算のみの場合はトランザクション不要
  
  認可:
    - API Routeで authz.check('tax:compute') を実行
    - 失敗時は403を返し、UseCase層には到達しない
  
  冪等性:
    - 計算のみのため冪等性考慮不要（同じ入力は同じ出力）
    - 結果をキャッシュする場合はRedisでキー管理（任意）

データモデル:
  読み取り:
    - tax_ratesテーブル: tax_categoryに対応する現在の税率を取得
    - tax_rulesテーブル: 適用期間による控除率の判定
  書き込み:
    - なし（計算結果はレスポンスのみ、永続化は呼び出し側の責務）

Allow Paths:
  - src/domain/tax/services/TaxCalculator.ts
  - src/domain/tax/usecases/CalculateTaxUseCase.ts
  - src/app/api/tax/compute/route.ts
  - tests/domain/tax/TaxCalculator.test.ts

禁止事項:
  - src/domain/tax/constants/TaxRates.ts の直接変更（データベース化済みのため）
  - 他ドメイン（billing, accounting）のコード変更
```

## 10. まとめ
control planeを成立させるには、「抽象的な良い設計」ではなく「**具体的な検証可能な仕様**」が必要です。

- **SR** では「型・制約・状態変化・不変条件」をデータスキーマとして固める
- **AC** では「Then」を自動テストでアサート可能な形（DB値・APIレスポンス・ログ）にする
- **DD** では「ファイルパス」と「トランザクション/認可/冪等性の境界」を物理的に特定する

これらを満たさない草案は自動採点で却下し、AIに具体化を促すことで、人間のレビューは「仕様の妥当性」に集中でき、コーディングエージェントは「指示された範囲での高精度な実装」に集中できます。

この設計により、仕様の質は個人の文章力に依存せず、再現性のある品質担保が可能になります。
