# X（Twitter）マーケティング戦略 v4

> v3→v4の主な変更点：
> - 投稿を137本→30本に絞り込み、各投稿の解像度を大幅に引き上げ
> - 3軸構成に再編（A：業務課題の可視化12本 / B：マネージドスクラッチの仕組み10本 / C：AI開発のリアル8本）
> - 批判系カテゴリ（旧Q群12本・N群10本・P群10本・H群5本）を廃止
> - 残存する批判要素は課題描写の文脈内でのみ使用
> - B2Bマッチングサービス提案時のXアカウント添付方針を明記
> - 業種横断の課題描写を大幅に追加（卸売・建設・不動産・商業施設等）
> - 「作ってみた」系は実績が出てから。先に出すと空虚になるため時期を後ろ倒し
> - フォロー戦略・リプライ戦略を維持しつつ、士業（税理士・公認会計士等）への認知を優先目標に追加

---

## 1. ポジショニングとプロフィール

### 狙うポジション

「パッケージのスキマを埋める専門家」。ERPやSaaSで効率化した"つもり"の企業に残るExcel業務・手作業のスキマを、業務理解に基づいたスクラッチ開発で埋める。コンサルでもSIerでもない第三のポジション。

### プロフィール設計

```
肩書き：パッケージのスキマを埋める業務システム構築 | 財務会計・経営管理 | AIコーディングエージェント

プロフィール文（160文字以内）：
SIer10年→外資コンサル6年。財務会計・経営管理のシステム導入とBPRを一貫して担当。
ERPやSaaSで効率化しきれない業務のスキマを、初期費用ゼロの月額制で埋める。
業務を構造化し、要件を定義し、AIエージェントで実装する。解約自由。
```

### アイコン・ヘッダー

- アイコン：顔出しが理想。抵抗があるならシルエット＋ドメインを示すアイコン
- ヘッダー画像：要件管理DBのスクリーンショットはNG（競争優位の源泉）。「業務フロー→システム→成果」のような抽象ビジュアル、またはBefore/After（Excel→システム画面）の対比画像

## 2. 投稿の基本方針

### 設計思想

v3までの137投稿案はコンサル・SIer批判が全体の4割を占めていた。批判系は初期のポジショニング確立には有効だが、「この人に頼みたい」と思わせるには課題描写と解決策の提示が必要。

本版では以下の3軸で30本に絞り込む。

- 軸A：業務課題の可視化（12本）── 「うちもそうだ」と思わせる
- 軸B：マネージドスクラッチの仕組み（10本）── 「こういう選び方があるのか」と気づかせる
- 軸C：AI開発のリアル（8本）── 「この人は実際に手を動かしている」と信頼させる

批判は「なぜ既存の選択肢ではダメか」を説明する文脈でのみ使う。批判自体を目的にしない。

### 投稿スタイル

- 具体的な数字と常識への反論が反応を取る
- 抽象的なポエムや意識高い系の発信はノイズに埋もれる
- noteの記事から切り出した一言を投稿し、記事への導線にする
- 「作ってみた」系はデモシステム完成後に開始（Year 0後半〜）

### 投稿頻度

| フェーズ | 時期 | X投稿頻度 |
|---------|------|----------|
| 在職中 | 〜2026年6月 | 週1回（ストック投稿の予約投稿） |
| Year 0前半 | 2026年7月〜12月 | 週2回 |
| Year 0後半〜 | 2027年1月〜 | 週2〜3回 |

在職中の30分は、投稿作成よりもストック蓄積とリプライに使う。30本のストックを予約投稿するだけでも半年以上持つ。

### B2Bマッチングサービス提案時のXアカウント方針

フォロワー数が少ない段階では、B2Bマッチングサービスの提案にXアカウントを添付しない。フォロワー数の少なさはマイナス印象のリスクが高い。

Xアカウントを提案に添付するタイミングの目安：フォロワー500人以上、または業界関係者からのエンゲージメントが一定量ある状態。

提案に添付すべきはnoteの記事リンク（特に記事2：kintone TCO比較）であり、Xではない。

### カテゴリA：業務課題の可視化（12本）

顧客が「うちの話だ」と感じる課題描写。業種横断で幅を持たせる。

| # | タイトル | 投稿テキスト |
|---|---------|-------------|
| A-01 | 月末の経理部 | 毎月25日を過ぎると経理部のExcelファイルが20個に増殖する。ERPから出した数字を部門別に組み替えて、配賦ロジックを手計算して、管理会計レポートに転記する。ERP入れたのに手作業が減らないのは「ERPの守備範囲外」の業務が放置されてるから。この"スキマ"を埋めるのが自分の仕事です。 |
| A-02 | 見積書のコピペ地獄 | 「見積書のフォーマット、お客様ごとに違うんです」。営業事務がExcelテンプレートを30種類管理してる会社、割と多い。ERPの販売管理には見積機能があるのに使えない。理由は単純で、取引先ごとの値引きルール・端数処理・備考欄の書式がパッケージの仕様に合わないから。 |
| A-03 | 受注から出荷までの空白 | SFAで商談管理→受注確定→ERPに手入力→出荷指示をメールで倉庫に飛ばす。この「受注確定からERP入力」の間に受注台帳というExcelがいる。なぜか。SFAの商談情報とERPの受注入力のデータ構造が違うから。項目のマッピングを人間がやっている。 |
| A-04 | 在庫の数字が合わない | 倉庫の実在庫とシステムの理論在庫が毎月ずれる。原因の8割は「出荷確定のタイミング」と「返品処理の反映遅れ」。ERPの在庫機能は正しく動いてる。問題はERPの外側で起きている出来事をリアルタイムにシステムに反映する仕組みがないこと。 |
| A-05 | 入金消込の職人芸 | 銀行のCSVを取り込んで、請求データと突合して、入金消込をする。振込人名義が請求先名と微妙に違う、まとめ払いで複数請求を合算してくる、消費税の端数が1円合わない。この職人芸を月末にベテラン1人が3日かけてやっている会社がある。 |
| A-06 | 工事の原価が読めない | 建設業。工事が終わるまで原価が確定しない。途中経過を知りたくても、購買の発注データ・外注の出来高・労務費の集計がバラバラの場所にある。現場所長がExcelで管理してるけど、複数現場を横串で見る手段がない。 |
| A-07 | テナント精算の闇 | 商業施設の管理会社。テナントごとに売上歩合・最低保証・共益費・販促費分担の計算ロジックが全部違う。契約書に書いてあるルールをExcelの数式に落として毎月精算してる。担当者が異動すると数式の意味が誰にもわからなくなる。 |
| A-08 | 予算策定という年中行事 | 毎年10月になると経営企画が各部門にExcelの予算テンプレートを配る。部門が入力→集約→調整→再配布→再入力。3往復して12月にようやく固まる。翌年4月、予実対比を始めた瞬間に「この科目の粒度が予算と実績で違う」と気づく。 |
| A-09 | 日報がただの作文になっている | 営業日報。CRMに商談情報を入力して、さらに日報を書く。上司は日報を読むが、CRMのデータは見ない。結果として同じ情報が2箇所に存在し、どちらも中途半端な精度。日報に書いてある定性情報がデータ化されず、分析にも使えない。 |
| A-10 | 属人化している与信管理 | 卸売業。得意先の与信枠をベテラン営業部長の頭の中で管理してる。根拠は「20年の取引経験」。本人がいないと受注判断が止まる。与信情報を構造化してシステムに載せれば、ルールベースで自動判定できる部分が8割ある。 |
| A-11 | 契約更新を忘れる不動産管理 | 不動産管理会社。300件の賃貸契約、更新時期がバラバラ。Excelの一覧表で管理してるが、フィルタをかけ忘れて更新漏れが年に2-3件。更新漏れ1件の損失は数十万円。アラート付きの管理画面があれば防げる話。 |
| A-12 | 部門をまたぐ承認が止まる | 購買申請→部門長承認→経理確認→発注。このフローが紙の回覧板かメール添付で回ってる。承認者が出張中だと1週間止まる。「急ぎなので口頭で了承もらいました」が常態化して、後から証跡がないと監査で指摘される。 |

### カテゴリB：マネージドスクラッチの仕組み（10本）

「こういう選択肢があるのか」と気づかせる。直接的な売り込みではなく仕組みの解説。

| # | タイトル | 投稿テキスト |
|---|---------|-------------|
| B-01 | 業務システムのサブスク | 業務システムを月額制で使う、という選択肢がある。初期費用ゼロ。月額は機能数に応じて決まる。合わなければ解約自由。SaaSと違うのは、自社の業務に完全に合わせたスクラッチ開発であること。SaaSの汎用性とスクラッチの柔軟性の間を埋めるモデル。 |
| B-02 | 半年ごとにシステムが育つ | マネージドスクラッチには半年ごとに機能数の20%分のクレジットが付く。10機能のシステムなら半年で2機能分の改修・追加ができる。「画面のここが使いにくい」「この帳票も出したい」という要望をクレジットで対応する。使い続けるほどシステムが業務にフィットしていく。 |
| B-03 | なぜ初期費用ゼロが成立するか | 「初期費用ゼロでスクラッチ開発なんて赤字では？」と聞かれる。答えはシンプルで、月額課金の継続で回収するから。12ヶ月で初期開発コストを回収し、13ヶ月目以降が利益になる設計。クライアントにとっては初期投資リスクがゼロ。提供者にとっては長期契約のインセンティブが働く。 |
| B-04 | 解約自由は自信の裏返し | 「解約自由」と聞くと太っ腹に見えるかもしれない。でもこれは自信があるから言える。業務に合ったシステムを月額で使えて、半年ごとに改善されて、それでも解約したいと思う顧客はほぼいない。解約自由はリスクではなく品質保証の一形態。 |
| B-05 | kintoneの3年コスト、計算したことありますか | kintoneを30人で使う。ライセンス月5.4万＋プラグイン月5万＝月10.4万。36ヶ月で374万。「安い」と思うかもしれない。でも内製する社員の工数を時給換算すると開発224万＋保守307万＝531万。合計905万円。外注なら1,034万。月額制のスクラッチ開発なら835万円で社員負荷はほぼゼロ。 |
| B-06 | SIerの見積もりが高い構造的理由 | SIerの見積もり＝人月単価×工数。人月単価には元請けマージン・管理費・オフィス維持費が乗る。さらに工数を減らすインセンティブが構造的にない。AI開発の生産性向上が価格に反映されるまでには、業界全体のコスト構造が変わる必要がある。待てない会社は別の選択肢を探すしかない。 |
| B-07 | 「ちょっと直して」のコスト問題 | 保守契約だけのシステムで「この項目名、変えてほしい」と頼むと見積もりが来る。3万円。ラベルを変えるだけで3万円。嫌な顔をすると「影響調査と回帰テスト含む」と言われる。マネージドスクラッチならクレジットで対応。ラベル変更は0.1クレジット。半年で2クレジット付くから、20箇所直せる。 |
| B-08 | クレジットの使い道カタログ | マネージドスクラッチのクレジット消費の目安。ラベル変更0.1、表示項目の追加0.2、帳票レイアウト変更0.3、新規画面（簡易）0.8、新規画面（複雑）1.0。半年で2クレジット付くから「帳票レイアウト2つ＋バリデーション変更3つ＋ラベル修正4箇所」みたいな組み合わせが現実的。 |
| B-09 | SaaSに「足りない」が出たとき | SaaSを導入して半年。業務が回り始めると「ここが足りない」が出てくる。SaaSベンダーに改修依頼→「ロードマップにあります（時期未定）」か「カスタマイズは別料金です」。マネージドスクラッチなら自社の要件に合わせて作っているから、半年ごとのクレジットで継続改善できる。 |
| B-10 | フェーズリリースの合理性 | 10機能を一括で作って本番稼働、ではない。3機能ずつPhaseを切ってリリースする。Phase 1が動いた時点でユーザから「ここ違う」が出る。それをPhase 2に反映できる。月額課金もPhase 1リリースから段階的に始まるから、全機能が揃う前から使い始められる。 |

### カテゴリC：AI開発のリアル（8本）

「この人は実際に手を動かしている」と信頼させる。技術自慢ではなく、業務システム開発の文脈でAIを語る。

| # | タイトル | 投稿テキスト |
|---|---------|-------------|
| C-01 | AIエージェントに渡す前の仕事 | AIコーディングエージェントにコードを書かせる。その前に必要なのは「何を作るか」の定義。業務フローを整理し、入出力を決め、バリデーションルールを洗い出し、例外処理を網羅する。この工程は人間にしかできない。AIが速く作れるほど、この定義の精度が成果物の品質を決める。 |
| C-02 | AIの開発速度、正直なところ | AIを使って開発速度が10倍になった、という話をよく見る。実感としては2-3倍が誠実な数字。ただし2-3倍の意味は大きい。従来3ヶ月かかる開発が1ヶ月で終わる。月額課金の回収が早まり、クライアントの待ち時間が減る。「10倍」より「1ヶ月で本番稼働」のほうが実務的に刺さる。 |
| C-03 | AIが間違えるパターン | AIが書いたコードで一番多いバグは「正常系は完璧だが異常系が甘い」。入力が空のとき、数値がマイナスのとき、日付が月末のとき。業務システムではこの異常系こそが命。テストケースを人間が網羅的に書いて、AIにぶつける。この品質管理工程を省略するとシステム障害に直結する。 |
| C-04 | 要件管理DBという武器 | 業務要件→システム要件→テストケースを一つのDBで管理している。要件が変わったら影響範囲が自動で見える。AIエージェントはこのDBを参照して実装する。「要件定義書.xlsx v12_最終_修正版2.xlsx」が存在しない世界。 |
| C-05 | TypeScript + Supabase + Next.jsを選ぶ理由 | 技術選定の基準は「自分が辞めても別のエンジニアが引き継げること」。TypeScript、Supabase、Next.jsはいずれもエンジニアの市場供給が多い。マイナーなフレームワークで作ると保守が属人化する。業務システムの技術選定は尖る必要がない。 |
| C-06 | 業務ロジックをコードにする翻訳作業 | 「月末締めの請求で、20日以降の出荷分は翌月請求にする。ただし得意先Aは15日締め」。この1文をif文に変換するのは簡単。問題は、このルールが経理のベテランの頭の中にしか存在しないこと。コードを書く前に、このルールを引き出して明文化する作業が全体の工数の半分を占める。 |
| C-07 | マスタデータの整備がAI活用の前提 | AIに業務データを食わせて分析したい、という相談を受ける。見てみると、顧客コードが3システムで別、商品カテゴリの粒度がバラバラ、部門コードが組織改編で崩壊してる。AI以前の問題。マスタデータの整備は地味だが、ここを飛ばすとどんなシステムも機能しない。 |
| C-08 | 「AIで全部できる」の危険性 | AIがコードを書ける→「じゃあ要件定義もAIで」→業務を知らないAIが業務を知らないまま設計→正確に間違ったシステムが高速に完成する。AIは「正しい指示を高速に実行する」ツール。指示の正しさを担保するのは人間の業務理解。ここを省略すると高速に失敗する。 |

## 5. 投稿以外のアクション

### フォロー戦略

- 紹介元候補（最重要）：税理士、公認会計士、社労士、中小企業診断士（ターゲット企業の顧問経由のリーチ）
- ターゲット企業の関係者：中堅企業の情シス部長、経営企画、DX推進室長
- 業界インフルエンサー：IT業界の有名人、DX推進で発信している人
- 同業・隣接領域：フリーランスエンジニア、ITコンサル個人事業主、業務コンサルタント
- 初期300〜500フォロー、フォロワー増加に伴いフォロー/フォロワー比率を調整

### リプライ戦略

最も重要なアクション。単なる「いいですね」ではなく、自分の専門性が伝わる一言を添える。

例：相手が「SIerの見積もり高すぎて困る」と投稿→「業務要件とシステム要件を分けて見積もりを取ると、どこにコストがかかってるか見えることがあります」

在職中の30分のうち、15分をリプライに使うのが最も費用対効果が高い。

### 引用リツイート戦略

他者の投稿を引用して自分の視点を加える。「これ、私の経験でも同じで…」「逆にこういうケースもあって…」

### DM戦略（Year 0後半〜）

LinkedInのDMアウトバウンドと連動。反応してくれた人へのフォローアップ。売り込みではなく関係構築。

### スペース（音声配信）

Year 1以降、フォロワー500〜1,000人超で検討。

## 8. v3から廃止したカテゴリ

以下はv3まで存在したが、顧客獲得に直結しない、または批判自体が目的になっていたため廃止する。

| 旧カテゴリ | 本数 | 廃止理由 |
|-----------|:---:|----------|
| Q群：コンサルファームのAI部門批判系 | 12本 | 自分の顧客獲得に無関係。批判しても仕事にならない |
| N群：ERP/SaaSのAI機能批判系 | 10本 | 批判しても仕事にならない。B-09（SaaSの「足りない」）で本質は言える |
| P群：AI活用の幻想 vs 現実系 | 10本 | 読み物としては面白いが送客につながらない |
| H群：技術ツール紹介系 | 5本 | エンジニア向けで顧客層と合わない。C-05で技術選定の考え方は伝わる |
| 旧A群：コンサル業界批判系 | 5本 | B-06（SIerの構造的理由）で本質は言える。批判を目的にしない |
| 旧B群：SIer開発批判系 | 5本 | 同上 |
| 旧O群：SIerにBPRは無理系 | 10本 | C-01, C-06で「業務理解の重要性」は伝わる。SIer批判として出す必要がない |
| 旧M群：ChatGPT/生成AI活用の現実系 | 12本 | C群に本質を凝縮。個別のAIツール批判は不要 |

### 残したもの

- ベンダーニュートラルの姿勢（SaaS推奨を含む）
- noteとXの連動構造
- リプライ戦略（専門性が伝わる一言を添える）
- 在職中のストック蓄積→退職後に集中公開の流れ
- フォロー戦略における士業（税理士・公認会計士等）の重視

### 変えたもの

- 批判系の比率を4割→1割以下に。批判は課題描写の文脈でのみ使用
- X投稿を137本→30本に絞り、各投稿の解像度を上げる
- 20%クレジットモデルをマーケティングの主軸に据える（旧：割引が前面）
- 財務会計だけでなく、卸売・建設・不動産・商業施設と業種を広げる
- 「作ってみた」系は実績が出てから。先に出すと空虚になる
