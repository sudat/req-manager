# note マーケティング戦略 v4

> v3→v4の主な変更点：
> - 記事テーマを18本→8本に絞り込み、各記事に構成案・想定読者・狙いを明記
> - コンテンツマーケティングの役割を「直接集客」から「信頼の補強材」に再定義
> - B2Bマッチングサービスでの提案添付を記事の主要用途に追加
> - SNSの効果指標に「士業からの認知・紹介件数」を追加
> - 記事カテゴリを4種類→3軸（業務課題の解像度 / マネージドスクラッチの仕組み / AI開発の現実）に再構成
> - 批判系コンテンツの比率を大幅に削減（課題描写の文脈でのみ使用）
> - 「書くべきコンテンツ4種類」を廃止し、3軸の設計思想に統合
> - 既存資産の記事化セクションを整理
> - タイムラインにB2Bマッチングサービス登録・提案準備を追加

## 1. noteの役割を定義する

noteの主目的は「信頼の補強材」であり、「直接的な集客装置」ではない。

中堅企業のCFOや情シス部長がnoteを巡回して「この人に頼もう」と連絡してくるシナリオは現実的ではない。noteが機能するのは、B2Bマッチングサービスの提案に添付する、リファラルで紹介された際に「この人のnote読んでみてください」と言ってもらえる、商談前に相手が検索して記事にたどり着く、といった場面。つまりnoteは「取る」ための道具ではなく「取りやすくする」ための環境整備。

直接的な集客はB2Bマッチングサービスとリファラルで行い、noteはその際の信頼補強材として機能させる。2社目以降のインバウンドパイプライン構築がnoteの本来の役割になる。

コンテンツマーケティングには半年〜1年のリードタイムがある。退職後に記事を書き始めても、検索流入が安定するのは半年後。だから在職中にストックを準備し、退職直後から使える状態にしておく。

### 効果指標

従来のPV・フォロワー数・問い合わせ数に加え、以下を追加する。

- 士業（税理士・公認会計士・中小企業診断士）からの認知件数
- 士業経由の紹介・問い合わせ件数
- B2Bマッチングサービスでの提案に記事を添付した件数と、その後の商談化率

Xのフォロワー500人より、税理士3人からの紹介ルートのほうがこのビジネスでは価値が大きい。

## 2. 記事設計の3軸

既存の戦略文書（18テーマ・137投稿案）はコンサル・SIer批判が全体の4割を占めていた。批判系は初期のポジショニング確立には有効だが、「この人に頼みたい」と思わせるには課題描写と解決策の提示が必要。

本版では以下の3軸で構成する。

- 軸1：業務課題の解像度（「うちもそうだ」と思わせる）
- 軸2：マネージドスクラッチの仕組み（「こういう選び方があるのか」と気づかせる）
- 軸3：AI開発の現実（「この人は実際に手を動かしている」と信頼させる）

批判は「なぜ既存の選択肢ではダメか」を説明する文脈でのみ使う。批判自体を目的にしない。

### コアメッセージ

「ERPやSaaSで効率化した"つもり"の企業に残る業務のスキマを、構造的に特定し、初期費用ゼロの月額制で確実に埋める。」

### ベンダーニュートラルの姿勢

SaaSやETLが最適ならそちらを提案する記事を書く。「スクラッチに固執しない」スタンスが逆説的に信頼を生む。

### 書き方の鉄則

- 記事の前半で「なぜこの問題がERPやSaaSだけでは解決しないのか」を業務構造から説明
- 後半で打ち手を見せる
- AsIs/ToBe業務フローを随所に織り込む
- 各記事に「向かない企業・向かないケース」を正直に書く。全方位に売ろうとしない姿勢が信頼を生む

### 記事構成テンプレート

```
1. 結論（この記事で言いたいこと）
2. 問題提起（なぜこのテーマが重要か）
3. 本論（具体的な解説、事例、AsIs/ToBe）
4. 結論（再掲 + 次のアクション）
5. CTA（無料相談への誘導）
```

### 記事1：業務システムを「サブスク」で使うという選択肢【軸2】

想定読者：SIerの見積もりに困っている中堅企業のIT担当・経営層

この記事の狙い：マネージドスクラッチの仕組みをゼロから説明し、「こういう買い方があるのか」という発見を提供する。

構成案：
1. 業務システムの調達方法は3つしかなかった（SaaS・パッケージ・スクラッチ）。4つ目の選択肢を提案する
2. なぜ従来のスクラッチ開発は高かったのか（人月商売の構造、AI以前の生産性）
3. AI開発で何が変わったか（開発コストの低下、ただし要件定義は変わらない）
4. マネージドスクラッチの仕組み（月額制、解約自由、半年ごとのクレジット）
5. どんな企業に向いているか（SIerの見積もりが予算を超える、SaaSでは要件が満たせない）
6. どんな企業には向かないか（100人以上が同時利用する大規模システム、ミッションクリティカルな基幹系）

記事の核心は「向かない企業」を正直に書くこと。全方位に売ろうとしない姿勢が信頼を生む。

### 記事2：kintoneで業務システムを作るのが本当にベストなのか【軸2】

想定読者：kintone導入を検討中、またはkintoneを使い始めて限界を感じている担当者

この記事の狙い：kintone名指し批判ではなく「内製 vs 外部委託」フレームで3パターンを比較。「kintoneが悪いのではなく、kintoneに向かない業務をkintoneで無理に実現しようとすることが問題」というトーン。

用途：この記事は三重の機能を果たす。
- (1) 検索流入のコンテンツ（「kintone 限界」「kintone コスト」等の検索ボリュームが大きい）
- (2) B2Bマッチングサービスでの提案添付資料（「kintone 開発」で探している企業への信頼材料）
- (3) 商談時の説明資料（TCO比較を具体的な数字で示せる）

構成案：
1. kintoneが得意なこと・向いている業務（シンプルなデータ管理、承認フロー、情報共有）
2. kintoneが苦手なこと（リアルタイム在庫管理、複雑な計算ロジック、帳票の細かいレイアウト制御、大量データ処理）
3. 3パターンの36ヶ月TCO比較表
    - ①kintone内製：約905万円（社員の構築・保守負荷が大。本業を圧迫）
    - ②kintone外注（伴走あり）：約1,034万円（ライセンス＋外注＋伴走の三重課金。最も割高）
    - ③マネージドスクラッチ（月額制）：約835万円（初期費用ゼロ・月額制・解約自由。社員負荷ほぼゼロ。機能制限なし）
4. 比較で見落とされがちなコスト（社員の学習コスト、プラグイン費用の積み上がり、外注の伴走支援費用）
5. 判断基準の提示：kintoneで十分なケース vs スクラッチが必要なケース
6. 本質的な比較軸：最終的にクライアントが比較するのは「今のExcel運用を続けるコスト」と「システム化するコスト」。月額の費用は派遣社員1名の人件費や属人作業の年間コストと比較されるべき

※ ②の存在がこの比較の鍵。①と③だけだと「安い vs 高い」の二択に見えるが、②を挟むことで「kintoneも外注したら高い。しかも機能制限がある」が可視化される。

※ BusinessModel_ManagedScratch.mdの数値をベースに構成。

### 記事3：「月末が怖い」経理部のためのシステム設計【軸1】

想定読者：月次決算に毎月10営業日以上かかっている経理部門

構成案：
1. 月次決算が遅い会社の典型パターン（ERPの数字は出る→手作業で加工→経営レポート完成が翌月10日以降）
2. 遅延の本質は「ERP外の業務」にある（部門配賦、管理会計の組み替え、連結調整、経営レポート加工）
3. SaaSで解決できるケース（ログラス、Adaptive Planning、Anaplanが合う会社とは）
4. SaaSでは解決できないケース（配賦ロジックが独自、管理会計の粒度がSaaSの標準に合わない）
5. スクラッチで「ERPの外側」を自動化するアプローチ
6. 実現後の姿：月次クローズ10営業日→3営業日の具体イメージ

ベンダーニュートラルを体現する記事。SaaSで解決できる場合はSaaSを推す。それでも残るスキマにマネージドスクラッチが効くという構成。

想定読者：卸売業・商社の営業管理・経理

構成案：
1. 典型的な卸売業の業務フロー（見積→受注→出荷指示→納品→請求→入金消込）

4. kintoneでどこまでできるか、どこで限界が来るか
5. マネージドスクラッチで構築した場合の機能構成（10機能の具体例）
6. 3年TCOの比較と、月額25万円の内訳

BusinessModelに記載された販売管理〜請求管理の12機能の具体像をベースにする。実際のシステム構成を見せることで「この人は絵空事ではなく本当に作れる」と思わせる。

### 記事5：建設業の工事原価管理がExcelを脱却できない理由【軸1】

想定読者：建設業の工事部長・経理部門

構成案：
1. 建設業の原価管理が難しい構造的理由（工事ごとに原価構造が異なる、完成工事高の認識基準、外注の出来高管理）
2. 既存パッケージの限界（OBIC、内田洋行等の建設業向けERPはあるが、工事進捗×原価のリアルタイム可視化が弱い）
3. 現場所長のExcel管理と本社経理のシステム管理が二重管理になる構造
4. 必要なのは「現場のデータをリアルタイムに集約する仕組み」
5. マネージドスクラッチでの実現アプローチ（現場入力UI→集約DB→経理向けダッシュボード）

建設業は中堅企業のIT投資が遅れている業界の一つ。原価管理の痛みが深い割に、フィットするSaaSが少ない。マネージドスクラッチの「スキマを埋める」ポジショニングと合致する。

### 記事6：AIがコードを書く時代に、業務システム開発はどう変わるのか【軸3】

想定読者：DX推進担当者、情シス部長、IT投資に関心のある経営層

構成案：
1. AIコーディングエージェントの現状と実力（何ができて何ができないか）
2. 開発コストが下がることの意味（SIerの人月単価の前提が崩れる）
3. コストが下がっても品質が下がらない条件（要件定義の精度）
4. 「AIで全部できる」と「AIは使えない」の間にある現実
5. 要件定義→AI実装→人間の品質管理という新しいワークフロー
6. これが意味すること：SIerに数千万払う以外の選択肢が生まれた

ポジショニングの知的根拠を提供する記事。「なぜ月額25万円でスクラッチ開発が成立するのか」の技術的背景を説明する。

### 記事7：「SIerに3,000万と言われた」から始まる話【軸2】

想定読者：SIerに見積もりを取ったが予算が合わなかった中堅企業

構成案：
1. SIerの見積もりが3,000万円になる内訳を分解する（PM費用、SE費用、テスト工数、管理間接費）
2. この3,000万円のうち「純粋な開発作業」はいくらか（実は3-4割）
3. 残りの6-7割は何に使われているのか（プロジェクト管理、品質管理、ドキュメント作成、ベンダー間調整）
4. この6-7割が「不要」なのではなく「別のやり方で代替可能」という視点
5. 1人の業務コンサルタント + AIコーディングエージェントで同じことをやるとどうなるか
6. 月額制にした場合の3年TCOと、SIer見積もりとの比較

SIerが悪いのではなく、SIerのコスト構造が中堅企業の予算感に合わないという構成。SIerを否定せず、「別の選択肢がある」と提案する。

### 記事8：使い続けるほど安くなる業務システム ── クレジット制度の設計思想【軸2】

想定読者：マネージドスクラッチに興味を持った人がさらに理解を深める記事

構成案：
1. SaaSの月額は「使い続けても変わらない」。むしろ値上げされることもある
2. SIerの保守は「使い続けるほど追加費用がかかる」。改修のたびに見積もり
3. マネージドスクラッチのクレジット制度の仕組み（半年ごとに20%、割引 or 機能追加の選択制）
4. 割引を選んだ場合の5年シミュレーション（月額が段階的に半額に近づく）
5. 機能追加を選んだ場合の5年シミュレーション（10機能が22機能に育つ）
6. クレジット消費カタログの具体例（「この改修にいくらかかるか」が事前にわかる）
7. なぜこのモデルが提供者にとっても合理的か（解約抑止、長期関係、アップセル機会）

TCO試算スプレッドシートの数字をそのまま使い、具体的なシミュレーションを見せる。「透明性」がこの記事の最大の武器。SIerの見積もりが不透明であることへのアンチテーゼ。
