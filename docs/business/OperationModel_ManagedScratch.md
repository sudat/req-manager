# マネージドスクラッチ 営業〜本稼働 実務設計書

## 本ドキュメントの位置づけ

BusinessModel_ManagedScratch.md で定義したビジネスモデル・料金体系・マーケティング戦略を前提に、営業段階から本番稼働までの実務オペレーションを定義する。特に概算見積もりの算定方法、フェーズ別の実タスクと工数、並列運用時のキャパシティ管理に焦点を当てる。

---

## 1. 概算見積もりの算定方法

### 基本単価

月額2.5万円/機能。クライアントには「10機能なら月額25万円」と伝える。年間コストを即座に暗算できるシンプルさが最優先。

初期費用はゼロ。月額課金のみ。解約時はシステムを回収（売り切りではない）。

### 機能タイプの定義

以下の5タイプに分類する。概算段階では全タイプ一律2万円/月。

| 機能タイプ | 概要 | 具体例 |
|-----------|------|--------|
| マスタ管理 | CRUD＋検索＋CSV取込 | 顧客マスタ、商品マスタ |
| 業務入力 | 状態遷移付きデータ入力 | 受注登録、出荷指示 |
| 帳票出力 | PDF生成＋メール/印刷 | 見積書、納品書、請求書 |
| レポート | 集計＋グラフ表示 | 売上レポート、ダッシュボード |
| ワークフロー | 承認ルート＋通知 | 金額別承認、稟議フロー |

### 正式見積もり時の難易度係数

概算は一律2.5万円/月。正式見積もり（Month 1後半）で難易度係数0.8〜1.5を適用する。

| 該当数 | 係数 | 意味 |
|-------|------|------|
| 0 | 0.8 | 単純なCRUD。中で完結、1件ずつ処理、ルール一律 |
| 1 | 1.0 | 標準。複雑性トリガー1つに該当 |
| 2 | 1.2 | やや複雑。2つに該当 |
| 3 | 1.5 | 複雑。3つ全てに該当。機能分割を検討 |

係数1.5が上限。これを超える場合は機能を2つに分割してカウントする方がクライアントにとって分かりやすい。

## 2. 複雑性トリガー（3概念）

機能が複雑になる本質的な理由は3つに集約される。初回診断時にクライアントへ共有し、正式見積もり時の係数説明の根拠とする。

### 概念①：境界をまたぐ

システムの外側とデータをやり取りする機能。相手側の都合（フォーマット、タイミング、エラー）への対処が必要になる。

該当パターン：
- 外部システムとのAPI連携（基幹、SFA、会計ソフト等）
- CSV取込でフォーマットが複数パターンある
- 双方向のデータ同期（片方向の取込ではなく、両方から更新が入る）
- 帳票の顧客指定フォーマット完全準拠（罫線位置、フォント、社印配置まで指定）
- 電子帳簿保存法対応（タイムスタンプ、検索要件）

kintoneとの対比：kintoneが最も苦手な領域。標準機能では片方向CSVバッチが限界。双方向連携やリアルタイムAPIはJavaScriptで無理やり書くか諦めるかの二択。

### 概念②：時間軸で束ねる

個々のトランザクションをある期間で集計・締め・突合する機能。1件ずつの入力は簡単でも、「月末に締めて集計する」「入金と請求を突合する」瞬間に複雑性が跳ね上がる。

該当パターン：
- 月次締め集計（締め日が顧客・部門ごとに異なる場合は特に）
- 入金消込（請求との突合、差額処理）
- 在庫の数量管理（業務判断に使う精度が求められる場合）
- 配賦計算・按分ロジック

kintoneとの対比：kintoneはトランザクション制御が弱く、同時更新での整合性保証ができない。集計もJavaScript頼みで保守不能化しやすい。

### 概念③：条件で分岐する

同じ機能なのに、対象（顧客、商品、部門、金額）によって処理ルールが変わる機能。分岐が掛け算になると「if文が増える」のではなく「ルールテーブルが必要になる」という質的な変化が起きる。

該当パターン：
- 顧客別単価 × 数量割引 × 期間割引の多段階価格計算
- 顧客ごとに異なる締め日
- 金額 × 部門 × 役職で変わる承認ルート
- フィールド単位の権限制御（ロール × 部門 × データ種別）

kintoneとの対比：kintoneのフィールド計算やプロセス管理は単純な分岐に対応可能だが、多段階の条件組み合わせはJavaScript必須。ルール変更のたびに開発者が必要になる。

## 3. 受注フロー（営業〜Month 1）

### フロー全体

```
初回商談（1-2h、無料）
  → 概算見積もり提示（商談当日〜翌日）
  → クライアント社内稟議（1-2週間）
  → 受注（発注書受領）
  → Month 1前半：全フェーズ業務ヒアリング＋DB設計
  → Month 1後半：Ph1開発＋正式見積もり提示
  → 乖離があれば合意調整
  → Month 2以降：Ph1本番投入〜
```

### 初回診断（1-2h）で聞くこと

自由に語らせると2時間では終わらない。こちらからフレームを提示して埋めてもらう。聞くのは3つだけ。

1. 誰が、何を、どこに入力/出力しているか → 機能の本数が決まる
2. 今それをやるのに何分/何人かかっているか → ROIの説明材料（月額の正当化）
3. それ、今困ってますか？の温度感 → Ph1-2-3の優先順位付け

加えて、複雑性トリガーの3概念を共有し「御社の業務でこれに当てはまるものはありますか？」と確認する。

### kintone比較の活用

初回診断で「kintoneでやるとしたらこうなる」「kintoneではこの要件は実現できない」を会話に織り込む。クライアントの意識に比較対象が生まれ、月額2万円/機能の高い安いを自分で判断できる状態を作る。

### 概算見積もり書の構成

| 項目 | 内容 |
|------|------|
| 機能一覧 | 初回診断で列挙した機能名と本数 |
| 月額 | 機能数 × 2.5万円/月 |
| 年間コスト | 月額 × 12 |
| 含まれるもの | 要件定義、設計、開発、テスト、データ移行、本番切替支援、操作マニュアル、保守 |
| 含まれないもの | 初回診断で確認した「境界をまたぐ」等の複雑性トリガー該当項目（該当した場合は正式見積もりで係数反映） |
| 正式見積もりの時期 | Month 1後半（要件定義完了後） |
| 概算の精度 | ±15%（複雑性トリガーの該当状況により上振れ/下振れ） |

概算時にバッファを10-15%乗せておき、正式見積もりで下げる方がクライアントの印象が良い。

### 概算→正式のギャップ管理

正式見積もり時の乖離は、複雑性トリガーの該当数で説明する。「初回診断では該当なしだった外部API連携が1件判明したので、受注登録の係数が1.0→1.2になりました」というロジック。概算時にトリガー概念を共有しておけば「あのとき話した3つのうち2つに当たりました」で済む。

## 4. フェーズ分割の設計

### 分割の原則

業務フローの上流から順に本番投入する。

| Phase | 機能群 | リリース理由 |
|-------|--------|-------------|
| Ph1 | マスタ管理、見積作成、営業日報、掲示板、承認WF | 業務の入口。データ入力が始まらないと後続が動かない。低リスクで使い始められる |
| Ph2 | 受注登録、出荷指示、納品書発行 | Ph1のマスタが溜まった状態で投入。受注フローの本体 |
| Ph3 | 請求書発行、入金消込、売上レポート | Ph2の実績データが1ヶ月分溜まってから意味が出る。月次締め系 |

### 要件詳細度の傾斜

Month 1で全フェーズの業務理解とスキーマ設計を一括で行うが、要件の詳細度はフェーズごとに傾斜をつける。

| フェーズ | Month 1での詳細度 | 理由 |
|---------|------------------|------|
| Ph1 | 画面項目レベルまで確定 | すぐ実装に入るため |
| Ph2 | 業務フロー＋主要な業務ルールまで確定 | Ph1稼働中にクライアントの解像度が上がる。細部はMonth 2で詰める |
| Ph3 | 業務フロー＋データ構造まで確定 | 月次締めのロジックは実データが溜まってから精緻化する方が手戻りが少ない |

この傾斜が正式見積もりの精度にも対応する。Ph1は確定、Ph2は±10%、Ph3は±20%。Ph3の±20%が概算バッファ内に収まっていれば追加稟議は不要。

## 8. Month 1：業務理解＋要件定義（須田 8日）

このフェーズの目的は「10機能のToBe業務要件を要件管理DBに格納し、クライアントと合意する」こと。設計書やパワポは作らない。

### 要件定義の全体フロー

AsIsヒアリングとToBe合意を明確に分ける。要件管理DBに登録するのはToBeであり、AsIsを聞いただけでは登録できない。

```
AsIsヒアリング（現行業務＋課題＋希望を聞く）
  → 須田がToBe素案を作成（「システム化後はこうなります」）
  → ToBe方針合意MTG（クライアントと方向性を合意）
  → 合意したToBeを要件管理DBに登録
  → 要件レビューMTGで詳細を確認・確定
```

ToBe素案は、AsIsヒアリングで得た「現行フロー」「課題」「こうなったらいいな」をもとに、須田がシステム化後の業務の姿を設計するもの。コンサル的な構想ドキュメントを作るのではなく、要件管理DBの業務タスク一覧として「誰が・何を・どの画面で・どういう順番でやるか」を並べる。

### 業務フローの表現方法

パワポで業務フロー図を作ると1機能あたり0.5〜1日かかる。これを回避するために以下で代替する。

- 要件管理DBの業務タスク一覧をプロセス順に並べて見せる（「この順番で業務が流れます」）
- 必要であればMermaid記法でシーケンス図を自動生成
- プロトタイプの画面遷移そのものが業務フローの代替になる（Month 2以降）

中堅企業の業務担当者は「フロー図」より「画面の順番」の方が直感的に理解できる。抽象的な図よりも動くものを見せた方が早い。

## 9. Month 2：Ph1開発＋レビュー（須田 4日 / FL 6日）

### Ph1の機能構成（4機能）

業務フローの入口。データ入力が始まらないと後続が動かない。

- 顧客マスタ管理
- 商品マスタ管理
- 見積作成＋PDF出力
- 承認ワークフロー（汎用）

## 15. BusinessModelの「稼働準備工数40人日」との関係

BusinessModel_ManagedScratch.md では「稼働準備工数40人日」と定義されている。これは須田のみの工数であり、FL工数は含まない。

本書のボトムアップ積算では須田の工数は23.5日。差分は16.5日。

この差分について考えられること：

- 本書のタスク積算では「すべてが計画通りに進む」前提で組んでいる。実際には以下のバッファ要因が発生する
  - 要件の手戻り（ToBe合意後にクライアント側の前提が変わる、キーマンが途中から参加して方針が覆る等）
  - FLの成果物の品質問題（想定以上の修正指示・再実装指示が必要になるケース）
  - データ移行の想定外（CSVのフォーマットが資料と実態で異なる、文字化け、データ不整合）
  - 本番切替後のQA対応が想定以上に膨らむ（操作ミス起因の問い合わせ、エッジケースのバグ）
  - クライアントの日程都合によるリスケ対応（MTGが延期→手待ち→再段取り）
- 初回案件は要件管理DBの運用自体が手探りであり、ツール側の調整工数も発生する
- 2案件目以降はテンプレート・指示書の再利用で効率化が進み、23.5日に近づく

結論として、初回案件は30〜35日、2案件目以降は23.5〜28日が現実的なレンジ。BusinessModelの40人日は安全側に振った数字としては妥当だが、2案件目以降も40日かかり続けることはない。案件を重ねるごとにBusinessModelの実効日当は改善していく。

## 16. 要件定義の効率化手法

### クライアント確認の方法

| 方法 | 適するケース |
|------|-------------|
| 要件管理DBのブラウザ画面を画面共有 | リアルタイムで修正しながら合意したいとき |
| 業務要件一覧をExcel/PDFでExport | クライアントが社内回覧したいとき |
| プロトタイプの画面遷移で確認 | Ph2以降、動くものがある状態 |

業務フロー図は原則作らない。要件管理DB上で業務タスクをプロセス順に並べれば、それが実質的なフロー。どうしてもフロー図が必要な場面（経営層への説明資料等）では、要件管理DBからMermaid記法で自動生成する。
